# VALIDATION — Gate 2A Exercise Catalogue Backend Completion

## Prompt classification

* **Prompt type:** VALIDATION
* **Gate:** Gate 2A — Exercise Catalogue Backend
* **Mode:** Independent, read-only validation
* **Implementation changes:** Not authorized
* **Development-schema changes:** Not authorized
* **Production access:** Not authorized
* **Deployment/publishing:** Not authorized
* **Gate 2B:** Must not start

## Objective

Independently validate the completed Gate 2A Exercise Catalogue Backend and its development-only migration re-baseline.

Do not rely solely on previous reports. Inspect the actual repository, migration chain, development schema, API implementation, tests, builds, and working-tree diff.

This prompt authorizes inspection and validation only.

## Permitted actions

You may:

* Inspect source files and Git history/status/diffs.
* Inspect the development migration ledger and physical schema.
* Run existing typechecks, tests, builds, and non-destructive diagnostic commands.
* Replay migrations in a new disposable validation schema.
* Drop only the disposable schema you created.
* Inspect runtime logs and authenticated/unauthenticated API boundaries.
* Use an independent reviewer or task agent for read-only review.

You must not:

* Edit, create, delete, rename, or format repository files.
* Repair or amend migrations.
* Modify the existing development schema or ledger.
* Seed or alter exercise records.
* Access production or shared external environments.
* Deploy or publish.
* Start Gate 2B.
* Convert a discovered problem into an implementation fix during this validation.

If any problem is found, stop and report it. A separate **FIX** prompt will be issued.

# 7. Validate concurrency protection

Inspect and validate the database-backed monotonic exercise-version mechanism.

Confirm:

* Every successful exercise mutation increments the version atomically.
* Stale updates return a conflict response.
* Scalar and mapping updates cannot both silently overwrite each other.
* Lifecycle transitions use the same compare-and-set protection.
* Activation validates the same version it commits.
* A concurrent invalidating edit and activation cannot produce an incomplete active exercise.
* Losing concurrent requests do not produce audit records or partial child-mapping changes.
* The version column and constraint used by the application are created entirely by canonical `0011`.

Run the existing deterministic concurrency tests.
