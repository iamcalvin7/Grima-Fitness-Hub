## Objective

Connect the existing Client Sessions interface to the verified Gate 2 booking backend.

After this build, authenticated Clients must be able to:

1. Discover real scheduled sessions.
2. View their upcoming and historical bookings.
3. Submit a real pending booking request.
4. Cancel an eligible future booking.
5. Reschedule an eligible booking atomically.
6. See truthful loading, empty, success, error and capacity-conflict states.

Preserve the existing visual design wherever possible. This is an integration build, not a redesign.

## Plain-English impact

The Sessions screen will stop being a simulation.

When a Client books, cancels or reschedules a session, the action will be processed by the server and stored in the database. Refreshing or reopening the app must show the same confirmed server state.

## Approved scope

### Included

## Stage 3 — Real booking request

Connect the existing confirmation action to the Gate 2 booking-creation endpoint.

Requirements:

* Send only fields required by the inspected API contract.
* Never send Client ID, tenant ID, role or privileged fields.
* Generate and use an idempotency key according to the backend contract.
* Disable repeat submission while the request is pending.
* Do not show success until the server returns success.
* Refresh session capacity and the Client’s bookings after success.
* Handle:

  * Validation failure
  * Session no longer available
  * Capacity reached
  * Duplicate/idempotent replay
  * Authentication failure
  * Unexpected server failure
* Preserve the Client’s selections when a recoverable error occurs.

Add tests proving:

* Successful booking persists in refreshed UI state.
* Double-clicking cannot create duplicate requests.
* Capacity conflict does not show false success.
* Validation and server errors are visible.
* Client/tenant identity is never taken from editable UI state.

## Stage 4 — Cancellation and rescheduling

### Cancellation

* Add a clear confirmation step before cancellation.
* Allow cancellation only when the server and current booking state permit it.
* Call the existing cancellation endpoint.
* Update the UI only after server success.
* Refresh booking and capacity data afterward.
* Show a useful error if the booking became ineligible.

### Rescheduling

* Use the existing atomic reschedule endpoint.
* Do not implement cancellation plus new booking as two frontend requests.
* Allow selection only from real available sessions.
* Prevent duplicate submission.
* Retain the original booking if the server rejects the reschedule.
* Refresh both affected sessions and the Client’s booking list after success.

Add tests for:

* Successful cancellation
* Failed/ineligible cancellation
* Successful atomic rescheduling
* Capacity conflict during rescheduling
* Original booking remaining visible after failed rescheduling
* Duplicate reschedule submission prevention
