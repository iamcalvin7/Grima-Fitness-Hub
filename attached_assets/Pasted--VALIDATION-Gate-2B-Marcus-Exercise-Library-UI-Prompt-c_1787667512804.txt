# VALIDATION — Gate 2B Marcus Exercise Library UI

## Prompt classification

* **Prompt type:** VALIDATION
* **Gate:** Gate 2B — Marcus Exercise Library UI
* **Mode:** Independent, read-only validation
* **Implementation changes:** Not authorized
* **Schema or migration changes:** Not authorized
* **Production/deployment:** Not authorized
* **Next gate:** Must not start

## Objective

Independently validate Task #44 against the approved Gate 2B build prompt and the authoritative Gate 2A API contract.

Do not rely only on the build report. Inspect the actual diff, implementation, tests, builds, and available runtime behavior.

If a defect is found, report it without fixing it. A separate **FIX** prompt will be issued.

## Permitted actions

You may:

* Inspect source, Git status, and diffs.
* Run existing tests, typechecks, and builds.
* Inspect API contracts and capabilities.
* Use the existing development preview.
* Use an existing safe Marcus/admin session if one is already available.
* Perform read-only browser inspection.
* Conduct an independent code and accessibility review.

You must not:

* Edit files.
* Add tests or fix defects.
* Change accounts, roles, permissions, schema, migrations, or data.
* Forge an admin session.
* Create exercise records during validation.
* Access production.
* Deploy or publish.
* Begin the next gate.

## 1. Scope and file ledger

Confirm the implementation is limited to:

* Exercise Library route and page
* Marcus/admin navigation
* Frontend guard
* BodyMap-compatible selection
* Focused frontend tests

Confirm no changes occurred to:

* Database schema or migrations
* Gate 2A API behavior
* Programmes or workout templates
* Workout execution
* Alternatives
* Personal bests
* Progressive overload
* AI
* Booking, wallet, commercial, notifications, or profile behavior
* Production/deployment configuration

Report the exact tracked and untracked file ledger and run `git diff --check`.

---

## 2. Authorization and navigation

Validate:

* `/exercise-library` is stable across direct navigation and browser back/forward.
* Desktop Sidebar exposes it only to authorized admin users.
* Mobile Burger Menu follows the same rule.
* Client and legacy-trainer users cannot access the management screen.
* The route guard fails closed while auth state is loading or unavailable.
* Direct URL access does not briefly expose protected management content.
* Frontend protection does not replace server authorization.
* No role or tenant identity is accepted from form state.

---

## 3. API-contract adherence

Compare every request and response used by the page with the actual Gate 2A API.

Confirm:

* Correct admin list and detail endpoints
* Correct create and patch payloads
* Correct activate, archive, and restore endpoints
* Correct pagination and filter parameters
* Only the six approved performance types
* Only canonical server muscle keys
* Correct equipment structure
* Correct media-reference behavior
* Current version included in mutations
* `409` conflicts handled without automatic overwrite
* No static programme data or browser storage used as authority
* No invented frontend-only persistent fields

---

## 4. Catalogue experience

Validate the server-backed list for:

* Loading
* Empty catalogue
* No search results
* API failure and retry
* Search
* Status filter
* Performance-type filter
* Muscle filter
* Equipment filter
* Filter clearing
* Pagination
* Draft, active, and archived distinctions
* Missing or broken media
* Long names and metadata

Confirm status is not communicated through colour alone.

---

## 5. Create and edit flows

Validate:

* New exercises are created as drafts.
* Creation does not automatically activate.
* Duplicate submissions are prevented.
* Backend validation is presented clearly.
* Recoverable errors preserve entered values.
* Existing records load from the server.
* Save and activate remain separate actions.
* Successful mutations refresh the current version.
* Unsaved-change protection covers editor closing, refresh, and relevant navigation.
* Raw database or internal errors are never displayed.

---

## 6. BodyMap, muscle, equipment, and performance metadata

Confirm:

* Existing BodyMap vocabulary is adapted to canonical server keys.
* No second muscle vocabulary was introduced.
* Primary and secondary muscles remain distinguishable.
* Duplicate mappings are prevented.
* BodyMap and form controls remain synchronized.
* Front/back views work.
* Non-visual accessible controls exist.
* Keyboard and touch interaction remain possible.
* Equipment duplicates are prevented.
* Performance types retain their approved distinctions.
* No personal-best or workout-logging logic was added.

---

## 7. Lifecycle and concurrency

Inspect implementation and directly run the focused tests proving:

* Complete draft activation succeeds.
* Incomplete activation returns readable validation feedback.
* Archive requires confirmation.
* Archive reason cannot be empty.
* Confirmed archive sends the reason.
* Archived exercise restores to draft.
* Lifecycle actions use the current version.
* Lifecycle `409` preserves the editor and displays an explicit reload option.
* Conflicting changes are not silently merged or retried.
* The UI does not claim success before server confirmation.

---

## 8. Responsive and accessibility review

Review desktop, tablet, and narrow-mobile behavior through available deterministic rendering or browser inspection.

Check:

* No unintended horizontal scrolling
* Touch-friendly controls
* Long-content handling
* Visible focus states
* Programmatically associated labels
* Accessible names for icon-only actions
* Keyboard-operable dialogs and BodyMap controls
* Dialog focus management
* Status not conveyed only by colour
* Useful loading and error announcements
* No hover-only critical actions

Report any accessibility or visual defect with severity.
