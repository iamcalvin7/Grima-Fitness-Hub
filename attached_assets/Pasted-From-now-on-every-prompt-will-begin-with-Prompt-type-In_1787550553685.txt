⸻

1. Purpose

Inspect the existing Grima Fitness Hub implementation before designing or building the new Workouts & Programming Engine.

The future system must support:

1. Programmes created by Marcus and published for all eligible clients.
2. Programmes created by Marcus and assigned to selected clients.
3. Workouts created by clients from an approved exercise library.
4. AI-generated workouts using the same approved exercise library.
5. Persistent set-by-set workout logging.
6. Personal bests for individual exercises.
7. Progressive-overload recommendations.
8. Context-aware alternative exercises.
9. Marcus-side review of client workout performance and progression.

Do not design from memory or rely solely on old reports. The actual codebase, database schema, routes, configuration and tests are the source of truth.

⸻

2. Known Starting Point to Verify

Previous project documentation suggests:

* Training Programme screens exist but programme data is largely demonstrative.
* Active Workout has some local interaction for sets, weights and rest timing.
* Workout persistence and complete workout history are missing or incomplete.
* Body-map muscle data may be hard-coded.
* Marcus HQ does not yet contain a complete programme-management system.
* Core data models for exercises, workouts, programmes, assignments and completions may not exist.

Treat these as assumptions requiring verification, not confirmed facts.

⸻

3. Target Product Architecture

The eventual engine is expected to contain the following connected domains.

3.1 Exercise Library

A Marcus-managed catalogue of approved exercises containing sufficient information for:

* Marcus-created workouts
* Client-created workouts
* AI-generated workouts
* Workout logging
* Personal-best calculation
* Progressive overload
* Exercise substitutions
* Muscle and body-map displays

Potential exercise information includes:

* Exercise name
* Description and instructions
* Demonstration media
* Primary and secondary muscles
* Movement pattern
* Equipment requirements
* Difficulty
* Unilateral or bilateral classification
* Bodyweight, weighted, assisted, timed or distance-based classification
* Safety notes
* Contraindication or limitation information
* Supported performance metrics
* Alternative exercises
* Active or archived status

This list is a target for gap analysis. Do not implement it during this gate.

3.2 Workout Templates

Reusable ordered collections of exercises that may define:

* Exercise order
* Sets
* Repetition targets or ranges
* Weight guidance
* Rest duration
* Tempo
* Effort or repetitions-in-reserve target
* Warm-up versus working sets
* Trainer instructions
* Optional or required exercises

3.3 Programmes

Structured collections of workout templates arranged across days and weeks.

The future system may require:

* Draft, published and archived states
* Programme versions
* Public availability
* Client-specific assignment
* Start date
* Expected training days
* Progress through the programme
* Assignment status
* Completion history

Published or assigned programme versions must not be silently altered by later Marcus edits.

3.4 Personal Workouts

Clients must eventually be able to create their own workouts from Marcus’s approved exercise library.

Personal workouts should:

* Use the same workout structure as Marcus-created workouts
* Be private from other clients
* Be visible to Marcus in his coaching role
* Support duplication and editing
* Support normal workout logging
* Contribute to personal bests and progression history

3.5 AI-Generated Workouts

AI-generated workouts must use the same workout and exercise structures as all other workouts.

The eventual AI builder should consider:

* Client goals
* Training experience
* Available time
* Selected training location
* Available equipment
* Injuries and limitations
* Requested muscle groups
* Recent training activity
* Recovery
* Previous exercise performance
* Existing assigned programme
* Exercise preferences and exclusions

AI must select only from approved exercises and its output must be validated by the server before being saved or started.

Do not build or connect an AI provider during this gate.

3.6 Workout Execution

Every workout source must eventually use one shared execution system:

* Marcus programme
* Public programme
* Client-created workout
* AI-generated workout

Workout execution should ultimately distinguish between:

* Planned workout
* Workout actually performed
* Planned exercise
* Exercise actually performed
* Planned sets
* Completed sets
* Warm-up sets
* Working sets
* Failed or abandoned sets
* Exercise substitutions
* Actual repetitions
* Actual weight
* Rest duration
* Effort
* Pain or discomfort
* Completion state

3.7 Personal Bests

The system must eventually recognise personal bests for individual exercises using authoritative completed workout data.

Potential personal-best types include:

* Heaviest successful working set
* Most repetitions completed at a recorded weight
* Estimated one-repetition maximum
* Highest completed workout volume for the exercise
* Maximum repetitions for bodyweight exercises
* Longest duration for timed exercises
* Distance or pace records where relevant

Not every record type applies to every exercise. The exercise definition should eventually determine which performance metrics are valid.

The authoritative personal best should be derived from completed workout history. A separate auditable personal-best event may be stored for celebrations, notifications and progress timelines.

3.8 Progressive Overload

The future progression engine should use actual workout performance rather than increasing weight automatically.

It may need to consider:

* Prescribed repetition range
* Actual repetitions
* Actual weight
* Effort or repetitions in reserve
* Performance across every set
* Rest duration
* Form breakdown
* Failed sets
* Pain or discomfort
* Recent exercise history
* Previous personal bests
* Available equipment increments

Progression should begin as deterministic, testable rules. AI may later explain recommendations but should not be the authoritative calculation engine.

3.9 Exercise Alternatives

Alternative exercises should eventually be evaluated using more than the primary muscle.

Potential matching information includes:

* Movement pattern
* Primary and secondary muscles
* Equipment availability
* Difficulty
* Unilateral or bilateral movement
* Client limitations
* Exercise contraindications
* Reason for requesting the replacement

Workout history must retain both the planned exercise and the exercise actually performed.

5. Personal-Best Inspection

Determine whether the existing app stores, calculates or displays exercise-specific personal bests.

Establish whether the current data can distinguish:

* Working sets from warm-up sets
* Completed sets from failed or abandoned sets
* Bodyweight exercises from externally loaded exercises
* Added-weight bodyweight exercises from unweighted versions
* Assisted exercises from unassisted versions
* Planned exercises from performed substitutions
* Actual one-repetition maximums from estimated values
* Timed exercises from repetition-based exercises
* Corrected logs from original logs
* Deleted or invalidated results
* Equivalent exercise variations from genuinely different exercises

Determine whether existing data could support:

* Heaviest successful working set
* Most repetitions at a recorded weight
* Estimated one-repetition maximum
* Highest exercise volume in one workout
* Maximum repetitions for bodyweight exercises
* Duration-based personal bests
* Personal-best date
* Originating workout and set
* Historical personal-best progression
* Marcus-side visibility
* Client-side celebrations
* Notifications
* Recalculation following an authorised correction

Assess the safest future architecture for:

1. Calculating authoritative records from completed-set history.
2. Storing auditable personal-best events.
3. Preventing duplicate personal-best celebrations.
4. Recalculating records after legitimate workout corrections.
5. Keeping personal bests tenant-safe and client-owned.

Do not implement personal-best calculations during Gate 0.

10. Stop Conditions

Stop and report immediately if:

* The real workout implementation cannot be located.
* Multiple incompatible workout models already exist.
* Existing workout data could be lost through the proposed direction.
* Exercise identity is inconsistent across current features.
* Tenant, organisation or ownership boundaries are unclear.
* Sensitive profile information lacks a clear permission boundary.
* Existing personal-best data cannot be traced to authoritative workout results.
* Inspection requires production access or mutation.
* Inspection would require installing or changing dependencies.
* Unrelated working-tree changes overlap the relevant files.
* The feature is materially higher risk than AMBER.

Do not solve a stop condition by changing the app.
