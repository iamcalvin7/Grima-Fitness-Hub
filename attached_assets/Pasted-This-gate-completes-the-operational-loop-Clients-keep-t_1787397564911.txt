Objective

Complete two connected requirements in one bounded gate:

1. Correct the confirmed concurrent idempotency replay issue in booking and rescheduling.

Stage 1 — Idempotency hardening canary

Booking creation

Add a deterministic integration test for:

* Capacity-one session.
* Same authenticated Client.
* Same session.
* Same idempotency key.
* Two concurrent booking requests.

Required outcome:

* Exactly one booking row exists.
* Both requests return the same booking identity.
* One response may be the original result and the other must be an idempotent replay.
* The second request must not return a false capacity conflict.
* Audit behaviour must remain correct and non-duplicative.

Correct the ordering by repeating the idempotency lookup inside the transaction after acquiring the relevant session lock and before capacity/availability rejection.

Preserve the existing database constraints and outer replay fallback.

Rescheduling

Inspect and test the equivalent concurrent same-key rescheduling path.

Required outcome:

* The original booking is transitioned only once.
* Only one replacement booking is created.
* Concurrent replay returns the same replacement result.
* No false capacity conflict.
* No duplicate audit mutation.
* No partial reschedule state.

Do not redesign the API contract.

Run the focused integration tests, API typecheck and existing booking suite. Proceed only when the canary is green.

Stage 2 — Role-aware Sessions separation

Split the Sessions experience by the authenticated server-backed role:

* client → existing verified Client Sessions experience.
* admin → new Marcus Sessions HQ.
* trainer → no Marcus controls; fail closed.
* Missing, loading or unknown role → fail closed until identity is resolved.

Requirements:

* Do not use URL parameters, local storage or editable frontend state as the authority for role selection.

* Server capabilities remain authoritative for every admin mutation.
* Marcus must not see Client-specific “Book Session,” “View Plan” or personal cancellation/rescheduling controls.
* Preserve all existing Client Gate 3 behaviour and tests.

Add automated tests proving each role branch.
