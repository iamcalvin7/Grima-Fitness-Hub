Task #36 — Training Wallet Top-Ups via Revolut Sandbox

Objective

Add real payment infrastructure to the existing Training Wallet using Revolut Merchant Sandbox.

The client journey should become:

Training Wallet
→ Add Training Value
→ choose amount
→ Revolut checkout
→ Apple Pay / Revolut Pay / card where supported
→ verified successful payment
→ cash-backed Training Value credited

This task is sandbox development only.

No live Revolut merchant account, live credentials, production deployment or real-money transactions are authorised.

⸻

Risk

AMBER for sandbox implementation

Escalate to RED before:

* live Revolut credentials
* real payment capture
* production webhook configuration
* production migration
* deployment
* real refunds/withdrawals

Do not cross that boundary in this task.

⸻

2. Commercial Principle

A wallet top-up is different from session revenue.

Example:

Client pays €100
→ €100 cash-backed Training Value added
This is NOT €100 session revenue.

Session revenue continues to be recognised only when wallet value is consumed through settled sessions.

Do not change Task #35 revenue logic.

⸻

3. Cash-Backed Wallet Value

Purchased Training Value must be distinguishable from:

* Marcus grants
* complimentary value
* promotional value
* manual adjustments

We need this provenance because only genuine purchased value may later become eligible for client withdrawal/refund.

Conceptually:

Purchased through Revolut      → cash-backed
Marcus complimentary grant     → non-cash-backed
Promotion                      → non-cash-backed

Do not implement withdrawals yet.

But the data model created now must preserve enough provenance to support them safely later.

⸻

Do not invent provider statuses if Revolut uses different terminology; map them explicitly.

6. Payment Methods

Use Revolut Checkout / Merchant infrastructure.

Where supported by the Revolut Sandbox/account configuration, expose:

* Revolut Pay
* Apple Pay
* card
* Google Pay if it comes automatically with the same supported checkout

Do not build separate payment integrations for each method.

They should all resolve into the same backend payment/top-up record.

If Apple Pay cannot be fully exercised in Revolut Sandbox, do not fake verification. Report the limitation and prove the underlying Revolut checkout/payment lifecycle instead.

⸻

7. Server Creates Payment

The frontend must not construct provider payment truth.

Expected flow:

Client chooses €100
↓
POST top-up request to Marcus backend
↓
Backend validates authenticated client
↓
Backend creates internal payment record
↓
Backend creates Revolut Sandbox order/payment
↓
Backend stores provider reference
↓
Frontend receives checkout information

Do not expose Revolut secret credentials to the client application.

⸻

8. Wallet Must Not Credit From Frontend Success

Critical rule:

checkout success page
≠
wallet credited

The wallet may only be credited after the backend has verified authoritative payment success.

Preferred source:

verified Revolut webhook

If Revolut’s current recommended architecture requires an additional provider-status verification step, follow it.

Never trust:

* query parameters
* browser redirect state
* frontend callback alone
* client-provided “paid” status

⸻

9. Verified Payment → Wallet Credit

When a top-up becomes authoritatively paid:

Transactionally:

payment marked paid
+
cash-backed wallet ledger movement created
+
payment linked to ledger movement
+
creditedAt recorded

Example:

Revolut payment: €100 paid
→ wallet +€100 cash-backed value

This must be idempotent.

⸻

10. Webhook Idempotency

Revolut may retry webhook delivery.

The same payment event arriving:

1 time
5 times
20 times

must still produce:

one €100 wallet credit

Use both:

* provider/payment identity
* database uniqueness/idempotency protection

where appropriate.

Do not rely solely on in-memory deduplication.

⸻

11. Payment Retry Behaviour

A user may:

* close checkout
* reload
* return later
* retry payment

Do not create duplicate wallet credits.

Clarify whether a retry:

* reuses an unpaid Revolut order, or
* creates a new provider order linked to a new attempt

according to Revolut’s recommended implementation.

Internal history must remain understandable.

⸻

12. Failed / Cancelled Payments

If payment:

* fails
* is cancelled
* expires

then:

wallet credit = €0

Payment history should show the outcome where useful.

A failed provider attempt must never affect booking/wallet availability.

⸻

13. Cash-Backed Provenance

Every wallet credit created from a real/sandbox payment must retain traceability:

wallet movement
→ payment/top-up
→ provider transaction/order

The system should eventually be able to answer:

How much of this client’s available wallet balance originated from actual purchased funds?

Do not attempt to calculate withdrawable balance using only the current total balance.

⸻

14. Spending Cash-Backed Value

Do not rewrite the existing booking engine.

Cash-backed value should enter the same wallet available balance used by:

booking maximum hold
→ class-close locked value
→ settlement

The booking engine should not care whether the value came from:

* payment
* Marcus grant
* promotion

unless future withdrawal provenance requires allocation tracking.

Inspect whether the ledger already supports source-aware consumption.

If additional allocation/provenance logic is required to preserve future cash-out correctness, report it before implementing a simplistic model that loses provenance.

20. Security

Required:

* provider secret server-side only
* webhook signature verification

Follow Revolut’s current security requirements.

Required:

→ webhook

26. Future Withdrawal Requirement

Do not build withdrawals now.

But explicitly verify that the model can later support:

Top up €200 cash-backed
Spend €150
Unused eligible amount €50
→ client may request withdrawal
→ Revolut partial refund against original purchase/payment

The model must distinguish this from:

Marcus grants €50 complimentary
→ not withdrawable as cash

If the implemented provenance cannot support this correctly, Task #36 is not complete.

⸻

27. Important Withdrawal Complexity

Inspect and document how cash-backed value will be allocated when a wallet contains mixed sources.

Example:

€100 cash-backed
€40 complimentary
Client spends €60

Before future withdrawals can be implemented, the system needs a deterministic rule for which value was consumed first.

Possible models include:

* cash-backed first
* complimentary first
* FIFO by ledger source

Do not make this policy silently.

For Task #36:

* identify the architecture requirement;
* preserve provenance;
* surface the future Product Owner decision if necessary.
