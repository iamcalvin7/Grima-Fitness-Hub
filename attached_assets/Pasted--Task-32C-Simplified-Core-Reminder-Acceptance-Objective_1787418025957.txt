# 1. Two-Hour Reminder

Add one deterministic test using the same pattern as the existing successful 24-hour test.

Create a confirmed booking with a future session.

Verify:

```text
session_reminder_2h
```

is created as pending.

Before due:

```text
visible = false
unread count = unchanged
```

At controlled due time:

```text
status = delivered
visible = true
unread count = +1
```

Run the processor again.

Expected:

```text
exactly one delivered 2h reminder
```

### PASS condition

One correct 2-hour reminder is delivered exactly once to the intended client.

---

# 2. Cancellation Suppression

Create a confirmed booking with pending reminders.

Cancel the booking before the reminder becomes due.

Run the reminder processor at/after the original due time.

Verify:

```text
no reminder becomes visible
unread count does not increase
```

The reminder may be marked `cancelled` or otherwise invalidated according to the existing architecture.

### PASS condition

A cancelled booking never produces a later session reminder.

---

# 3. Reschedule Suppression

Create and confirm a booking for:

```text
Monday 17:00
```

Verify reminder scheduling exists.

Reschedule it to:

```text
Tuesday 10:00
```

Follow the actual existing booking state model.

Verify:

* reminders tied to Monday 17:00 cannot deliver;
* if rescheduling returns the booking to pending, no new confirmed-session reminders are active until Marcus confirms;
* after the replacement booking is confirmed, reminder scheduling corresponds to Tuesday 10:00;
* notification/deep-link context references the replacement booking/session.

### PASS condition

The client never receives a reminder for the old session time after rescheduling.

---

# 4. Correct Client / Recipient Isolation

Create:

### PASS condition
