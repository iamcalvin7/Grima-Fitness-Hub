# Task #33 — Credits & Payment Model Inspection

## Objective

Define the commercial model for Sessions & Booking before implementing credits, payments, deductions, refunds, or entitlement rules.

Do **not** build payment or credit behaviour yet.

The goal of this task is to inspect the live codebase, identify what already exists, map the booking lifecycle against commercial consequences, and return a clear product decision model for approval.

The Sessions flow is now substantially complete in development:

```text
Marcus creates availability
→ Client requests booking
→ Marcus confirms/rejects
→ In-app notifications
→ 24h / 2h reminders
→ Session takes place
→ Marcus records attended / no-show
→ Client history updates
```

The missing commercial layer is:

```text
What does a session cost?
When is the client charged?
What happens to credits when bookings change?
```

# 13. Ledger Principle

If credits are recommended, evaluate whether a ledger-style model is preferable to a mutable integer such as:

```text
credits = 4
```

A robust model may instead record movements such as:

```text
+10 package purchase
-1 session consumed
+1 cancellation restoration
-1 no-show
```

The purpose is auditability and protection against balance corruption.

Do not build this yet.

Report whether a ledger is justified for Marcus's current product scale.
