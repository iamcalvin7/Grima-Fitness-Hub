# BUILD — Gate 2C Exercise Catalogue Import

## Prompt classification

* **Prompt type:** BUILD
* **Gate:** Gate 2C — Exercise Catalogue Import
* **Risk level:** Amber
* **Authorized environment:** Development only
* **Gate 2A backend:** Complete and authoritative
* **Gate 2B Marcus Exercise Library:** Complete and authoritative
* **Schema or migration changes:** Not authorized
* **Production access:** Not authorized
* **Deployment/publishing:** Not authorized

## Objective

Migrate the existing bundled/static exercise content into the server-authoritative Exercise Catalogue so Marcus begins with a useful, real exercise library rather than an empty database.

This is a content-import and reconciliation gate—not a database-schema migration.

The imported catalogue must:

* Use the Gate 2A exercise domain and API rules.
* Be visible and manageable through the Gate 2B Marcus Exercise Library.
* Preserve valid existing exercise information.
* Avoid fabricating missing coaching or safety content.
* Activate only exercises that satisfy the authoritative activation contract.
* Keep incomplete or ambiguous exercises as drafts.
* Be reproducible, tenant-safe, auditable and idempotent.
* Never overwrite an exercise Marcus has already changed manually.

Do not cut programmes, client workouts or workout execution over to the new catalogue in this gate.

* Relevant tests and documentation patterns.

Produce an inventory before importing anything:

* Static source files.
* Total source records.
* Unique exercise names.
* Unique proposed slugs.
* Duplicate or near-duplicate exercises.
* Fields available in the source.
* Fields missing from the source.
* Muscle values requiring mapping.
* Equipment values requiring mapping.
* Performance types requiring mapping.
* Invalid or unsupported media references.
* Exercises that can satisfy activation requirements.
* Exercises that must remain drafts.
* Existing database records that may conflict.

Do not treat old screenshots, demo presentation text or unrelated programme labels as canonical exercise records.

# 2. Stop conditions

Stop without importing if:

* No single credible static exercise source can be identified.
* The intended development tenant cannot be resolved safely.
* No legitimate development audit actor is available.
* Importing would require a schema or migration change.
* Importing would require weakening Gate 2A validation.
* Source values cannot be mapped to canonical muscles or performance types without material product decisions.
* Existing database records would need to be deleted or overwritten.
* The import cannot be made idempotent.
* A production or shared external environment would be required.
* The source contains conflicting exercise definitions that cannot be resolved objectively.
* Required content would have to be invented.

If blocked, return:

`BLOCKED — GATE 2C DATA DECISION REQUIRED`

Include a concise decision table listing every unresolved exercise or mapping.

# 3. Canonical import mapping

Create one explicit, reviewable mapping from the legacy/static exercise content to the Gate 2A contract.

For each exercise, determine only from existing source evidence:

* Name
* Deterministic slug
* Description, if available
* Instructions, if available
* Performance type
* Difficulty, if supported and available
* Laterality, if supported and available
* Primary muscle
* Secondary muscles
* Equipment
* Coaching notes, if supported and available
* Safety information, if supported and available
* Media reference, if compatible
* Import status:

  * Active candidate
  * Draft because incomplete
  * Blocked because ambiguous
  * Excluded because it is not genuinely an exercise

Requirements:

* Trim accidental whitespace.
* Preserve meaningful names and wording.
* Do not rewrite exercise instructions creatively.
* Do not invent muscles, equipment, safety notes or performance metadata.
* Use only canonical server muscle keys.
* Use only the six approved performance types.
* Normalize equipment through the supported server structure.
* Prevent duplicate primary/secondary muscle mappings.
* Prevent duplicate equipment mappings.
* Use server-generated IDs.
* Do not import tenant IDs, owner IDs or lifecycle versions from static data.
* Do not treat programme-specific sets, repetitions, rest times or loads as permanent exercise-definition fields.
* Do not import personal-best or workout-history information.

If two records are semantic duplicates, do not silently choose one. Resolve only objectively identical formatting variants; otherwise report the conflict.

# 4. Import mechanism

Implement the smallest supported, reproducible import mechanism that follows existing project conventions.

Requirements:

* Development-only execution.
* Explicit target tenant.
* Legitimate audit actor.
* Dry-run mode before writes.
* Exact proposed create, skip, conflict, draft and activation counts.
* Idempotent repeated execution.
* Transactional behavior where supported.
* Stable slug-based reconciliation.
* No destructive deletion.
* No blind upsert that overwrites manual changes.
* No direct mutation that bypasses domain validation, capabilities, tenant rules or auditing.
* No browser storage.
* No runtime dependency on frontend static data after import.
* Clear failure output without secrets or raw connection values.

Preferred behavior for an existing slug:

* If the existing record is demonstrably identical to the import definition, skip it.
* If it differs, report a conflict and preserve the existing record.
* Never replace Marcus’s current database record automatically.
* Never reset an existing version.
* Never change an existing lifecycle state automatically.

The import manifest may remain version-controlled as reproducible bootstrap content, but the database must be the runtime authority.

---

# 5. Draft and activation policy

Every imported record must first satisfy normal creation rules.

## Active exercises

An exercise may be activated only when:

* All Gate 2A activation requirements are satisfied.
* Performance type is unambiguous.
* Required muscle information is valid.
* Equipment mappings are valid.
* Required instructions or other activation fields exist.
* The normal activation service accepts it.
* The audit record succeeds.

Do not insert an exercise directly as active if doing so bypasses the approved lifecycle.

## Draft exercises

Keep an imported exercise as a draft when:

* Required content is missing.
* Muscle mapping is ambiguous.
* Performance type is uncertain.
* Equipment cannot be mapped confidently.
* Media information is invalid but non-essential.
* Activation validation rejects it.

Draft status is preferable to fabricated data.

The final report must list every draft and the exact missing or ambiguous information Marcus needs to review.

# 6. Development-data safety

Before writing:

* Record the existing development exercise count by lifecycle state.
* Record existing slugs.
* Run the importer in dry-run mode.
* Confirm no existing record will be overwritten, archived, restored or deleted.
* Confirm the target tenant and audit actor without exposing sensitive identifiers in the report.

During import:

* Use only the intended development tenant.
* Preserve tenant isolation.
* Stop safely on unexpected conflict.
* Do not partially apply a logically atomic record with missing child mappings.
* Do not create cross-tenant muscle or equipment mappings.
* Do not reset or reseed unrelated development data.

After import:

* Reconcile created, activated, drafted, skipped and conflicted counts.
* Confirm no unintended record changed.
* Confirm audit records exist.
* Confirm every imported exercise has valid tenant ownership.
* Confirm all versions remain positive and monotonic.

Do not perform destructive cleanup if verification fails. Stop and report the exact state.
