## 3. Exercise domain

Create an additive tenant-owned exercise domain following existing Drizzle/PostgreSQL conventions.

Recommended schema module:

```text
lib/db/src/schema/exercises.ts
```

Use the actual project naming conventions if they differ.

### 3.1 Exercise record

The exercise record must support:

* UUID identity
* Tenant ownership
* Name
* Tenant-unique slug
* Lifecycle status
* Performance type
* Movement pattern
* Unilateral/bilateral classification
* Description
* Client-visible instructions
* Difficulty
* Default rest duration
* Client-visible safety notes
* Internal Marcus notes
* Optional media reference
* Created-by actor
* Updated-by actor
* Created timestamp
* Updated timestamp

Lifecycle:

```text
draft → active → archived
archived → draft → active
```

Rules:

* A restored exercise returns to `draft`.
* Activation requires explicit validation.
* No hard-delete API is permitted.
* Archived exercises remain readable through Marcus/admin APIs.
* Archived exercises are excluded from normal client discovery.
* UUID is the authoritative exercise identity.
* Slug must be unique within the tenant.
* Slug may change while draft.
* Once activated, slug should remain stable unless a separately audited administrative correction is required.

Adapt nullable fields carefully so draft creation is practical, while activation still requires a complete valid record.

### 3.2 Performance types

Support exactly these version-one performance types:

```text
weight_reps
bodyweight_reps
added_weight_reps
assisted_reps
duration
distance_time
```

The API must reject unknown performance types.

This gate does not calculate PBs, but the exercise type must be suitable for later performance-specific validation.

### 3.3 Difficulty

Use an explicit validated value consistent with the existing project’s enum conventions.

Recommended values:

```text
beginner
intermediate
advanced
```

If the current app already has a stronger compatible vocabulary, document and reuse it rather than creating a competing one.

### 3.4 Exercise-muscle mappings

Create a tenant-safe child model supporting:

* Exercise
* Muscle key
* Role:

  * `primary`
  * `secondary`
* Creation timestamp

Requirements:

* A muscle may appear only once per exercise.
* Every active exercise requires at least one primary muscle.
* Child and parent must belong to the same tenant.
* Use a canonical server-side muscle vocabulary.
* Inspect current `BodyMap` and programme terminology when defining the initial vocabulary.
* Do not modify `BodyMap` in this gate.
* Report legacy muscle terms that do not map cleanly.
* Do not silently merge ambiguous terms.

### 3.5 Exercise-equipment mappings

Create a tenant-safe child model supporting:

* Exercise
* Normalised equipment key
* Whether the equipment is required
* Creation timestamp

Requirements:

* The same equipment key may appear only once per exercise.
* Equipment keys must be normalised and non-empty.
* Child and parent must belong to the same tenant.
* Do not build a separate equipment-management interface in this gate.

### 3.6 Media

Do not introduce a media provider or upload system.

If the schema contains an optional media reference:

* Follow existing safe asset/path conventions.
* Keep the field nullable.
* Validate its format.
* Do not fetch or verify external media during this gate.
* Do not create an unsupported foreign key to a nonexistent asset table.

Document the chosen approach.

## 4. Activation validation

An exercise may become active only when:

* It has a non-empty name.
* It has a valid tenant-unique slug.
* It has a valid performance type.
* It has a movement pattern.
* It has client-visible instructions.
* It has a valid difficulty.
* It has at least one primary muscle.
* All muscle and equipment mappings belong to the same tenant.
* Default rest, when present, is positive and within a reasonable validated bound.
* Required fields satisfy database and API constraints.

Activation must be transactional.

A failed activation must leave the exercise in draft state.

---

## 5. Capabilities and authorization

Extend the existing capability vocabulary without changing unrelated capability behavior.

Required capabilities:

```text
exercises:read
exercises:manage
exercises:archive
```

Role behavior for version one:

### Client

* May read active exercises in their tenant.
* Cannot view drafts or archived exercises.
* Cannot view internal Marcus notes.
* Cannot create, update, activate, restore or archive exercises.

### Marcus/Admin

* May list and view all tenant exercises.
* May create and update drafts.
* May update allowed active-exercise metadata.
* May activate exercises.
* May archive exercises.
* May restore archived exercises to draft.
* May view internal notes.

### Legacy trainer

* Receives no exercise access by default unless the current approved capability architecture explicitly says otherwise.
* Do not broaden legacy trainer permissions silently.

All authorization must be enforced by the API.

Frontend visibility is not a security boundary.

## 6. API

Follow existing route, error-envelope, validation and registration conventions.

Use the project’s established `/admin` structure where appropriate.

### 6.1 Client exercise API

Implement authenticated tenant-scoped endpoints equivalent to:

```text
GET /api/exercises
GET /api/exercises/:id
```

Client behavior:

* Return active exercises only.
* Apply tenant filtering.
* Support pagination.
* Support safe search.
* Allow appropriate filters such as:

  * Muscle
  * Equipment
  * Performance type
  * Difficulty
* Return client-safe fields only.
* Never return internal Marcus notes.
* An invisible, archived, draft, cross-tenant or missing exercise returns the project’s safe not-found response.

### 6.2 Marcus/admin exercise API

Implement capability-protected endpoints equivalent to:

```text
GET    /api/admin/exercises
GET    /api/admin/exercises/:id
POST   /api/admin/exercises
PATCH  /api/admin/exercises/:id
POST   /api/admin/exercises/:id/activate
POST   /api/admin/exercises/:id/archive
POST   /api/admin/exercises/:id/restore
```

Management behavior:

* Tenant and actor are derived from the authenticated session.
* Never accept tenant ownership from the request body.
* Create exercises initially as drafts.
* Create/update muscle and equipment mappings transactionally.
* Reject cross-tenant child identifiers.
* Return stable error codes and safe messages.
* Do not provide a hard-delete route.
* Archive requires a non-empty reason.
* Restore returns the exercise to draft.
* Activation uses the complete activation validator.
* State-transition conflicts return `409`.
* Validation errors follow the existing API convention.
* Audit failures must cause the related mutation to fail.

If the project’s established REST conventions require different literal paths, use them and document the decision. Preserve the behavioral contract above.

## 8. Database constraints and indexes

Use database enforcement wherever practical.

Required protections include:

* Tenant-safe exercise foreign keys
* Unique tenant/slug
* Unique exercise/muscle
* Unique exercise/equipment
* Valid lifecycle status
* Valid performance type
* Valid muscle role
* Non-negative or positive numeric bounds
* Tenant indexes for catalogue queries
* Search-supporting indexes where justified
* No hard cascade that could destroy future historical references

Cross-row activation requirements, such as at least one primary muscle, must be enforced transactionally by the service.

Do not introduce destructive schema operations.
