# 3. 24-Hour Reminder Test

Create a confirmed booking whose session is sufficiently in the future.

Verify that:

1. A `session_reminder_24h` record exists.
2. It begins as `pending`.
3. It is excluded from the client's notification inbox.
4. It is excluded from unread count.
5. Before `scheduledFor`, processor run does not deliver it.
6. At/after the valid due point, processor delivers it.
7. Status becomes `delivered`.
8. It now appears in the client's notification list.
9. Unread count increases by exactly 1.
10. It references the correct booking/session.
11. It contains the correct event type.
12. Running the processor again does not create or deliver another 24h reminder.

Expected:

```text
PASS — exactly one delivered 24h reminder
```

# 7. Reschedule Suppression & Replacement

This requires exact occurrence validation.

Create:

```text
Original session:
Monday 17:00
```

Confirm and create pending reminders.

Reschedule to:

```text
Replacement session:
Tuesday 10:00
```

Verify:

1. Old occurrence reminder rows are invalidated.
2. Old Monday reminders can never deliver.
3. If rescheduling returns booking to `pending`, no new confirmed reminder is scheduled yet.
4. After replacement booking becomes confirmed, applicable reminder rows are scheduled against Tuesday 10:00.
5. Event identity references the new occurrence timestamp.
6. Delivered reminder deep-links to the replacement booking/session.

Expected:

```text
PASS — no stale reminder survives rescheduling
```
