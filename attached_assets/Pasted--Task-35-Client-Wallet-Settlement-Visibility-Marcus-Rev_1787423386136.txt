# Task #35 — Client Wallet Settlement Visibility + Marcus Revenue Dashboard

## Objective

Expose the already-built commercial engine clearly to both sides of the product.

The system already supports:

* training-value holds
* class-close price locking
* hold reduction and release
* attendance settlement
* no-show charge/waive
* immutable commercial history

This task should make those outcomes visible and useful.

Do **not** introduce new pricing logic, payment providers, top-ups, refunds, subscriptions or revenue calculations independent from the existing ledger.

The core principle is:

```text
Client settlement
→ wallet deduction visible

Same settled movement
→ Marcus revenue visible
```

Revenue must come from the same settled commercial source of truth.

---

## Risk

**AMBER**

This touches commercial reporting and client wallet presentation.

Inspect the existing ledger and settlement implementation before building.

If the existing data model does not provide a reliable settled-value source, stop and report before inventing a parallel revenue model.

No production migration unless separately approved.

---

# 1. Revenue Definition

For this task:

> Revenue = settled training value actually consumed from a client booking.

Count as revenue:

### Attended booking

```text
locked value = €25
attended
→ €25 consumed
→ €25 revenue
```

### Charged no-show

```text
locked value = €25
no-show
Marcus chooses charge
→ €25 consumed
→ €25 revenue
```

Do **not** count:

* pending holds
* confirmed booking holds
* maximum holds
* released hold value
* waived no-shows
* rejected bookings
* cancelled bookings where value was released
* complimentary value merely granted to a wallet
* unsettled commercial reservations

Do not treat booked value as earned revenue.

---

# 2. Single Source of Truth

Do not add a separately maintained mutable field such as:

```text
revenueTotal
```

if it can drift from the commercial ledger.

Marcus revenue should be derived from the authoritative settled/consumed ledger movements or equivalent existing immutable settlement records.

Required invariant:

```text
Client settled deduction
=
Marcus recognised session revenue
```

for the same booking.

---

# 3. Inspect Existing Ledger First

Before implementation, identify exactly:

* movement types representing holds
* hold reduction/release
* attendance consumption
* no-show charge
* no-show waiver
* manual adjustments
* grants
* commercial settlement references
* booking/session linkage
* timestamps used for settlement

Report which movement(s) will be treated as revenue-bearing.

Do not infer revenue from booking status alone if the ledger already records the actual settled amount.

# 10. Revenue Date Basis

Revenue should be recognised using the timestamp of the actual settlement/consumption movement.

Do not use:

* booking-created date
* booking-confirmed date
* class-close date

unless the commercial engine actually settles at that moment.

For the approved model, settlement occurs after attendance/no-show decision, so the settled movement timestamp is the correct reporting basis.

---

# 11. Revenue Timezone

Use the existing Europe/Malta display/reporting conventions.

For period boundaries such as:

* Today
* This week
* This month

calculate periods consistently.

Do not accidentally classify a late-night settlement into the wrong local day because the stored timestamp is UTC.

# 12. Marcus — Session Revenue

Within session detail / Class pricing / Commercial detail, show revenue per participant.

Example:

| Client   | Outcome           | Settled value |
| -------- | ----------------- | ------------: |
| Client A | Attended          |           €25 |
| Client B | Attended          |           €25 |
| Client C | No-show · Charged |           €25 |
| Client D | No-show · Waived  |            €0 |

Then:

```text
Session revenue: €75
```

Revenue should come from actual settled amounts, not the class rate multiplied blindly by participant count.

# 16. Revenue vs Wallet Top-Ups

Important:

**Wallet top-ups are not session revenue in this dashboard.**

A future client purchase of €200 adds training value/liability but does not mean Marcus has delivered €200 of training.

Task #35 revenue specifically represents:

```text
training value consumed through settled sessions
```

Keep this distinction explicit so the future payment integration does not corrupt revenue reporting.

---

# 17. Complimentary / Marcus-Granted Value

Inspect how manually granted training value should appear in revenue.

For this initial operational dashboard, if a client consumes €25 of complimentary training value, determine whether the existing ledger tracks source provenance.

Do not silently treat it as cash revenue if it was not cash-backed.

If source provenance is not yet available, report this limitation.

Preferred future distinction:

```text
Session value consumed
Cash-backed revenue
Complimentary value used
```

but do not over-engineer it in this task unless the existing data supports it cleanly.

# 19. Client Permissions

Client can view only:

* their wallet
* their ledger/activity
* their session commercial outcomes

They cannot query another client's wallet or transaction history.

Server-side enforcement required.

---

# 20. Marcus Permissions

Only authorised Marcus/admin capabilities may access:

* aggregate revenue
* other clients' settlement values
* wallet adjustments/history where already authorised

Follow the existing capability system.

---

# 21. API Design

Prefer dedicated read APIs derived from existing authoritative data.

Conceptually:

```text

GET /api/wallet/activity
```

and operator:

```text

GET /api/admin/revenue/activity
GET /api/admin/training-sessions/:id/commercial-summary
```

Use existing route conventions rather than these exact paths if different.

Do not make frontend components calculate commercial truth from raw unrelated records.
