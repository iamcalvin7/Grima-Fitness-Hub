# Task #36 — Stripe Wallet Payment Safety & Regression Recovery

## Objective

Complete the safety verification for Stripe Test Mode wallet top-ups and restore the commercial/API integration suite to a fully green state.

Do not add new payment features.

The current implementation already supports:

* €50 / €100 / €200 wallet top-ups
* hosted Stripe Test Mode Checkout
* server-side wallet crediting
* signed webhook processing
* Test Mode secret enforcement
* terminal-state protection
* wallet top-ups excluded from session revenue

This task proves financial integrity.

---

## Risk

**AMBER — Test Mode financial-integrity verification**

No production Stripe account.

No live money.

No production migration.

---

# 1. Successful Payment

Using Stripe Test Mode, verify one successful €50 top-up.

Expected:

```text
Top-up:
pending → paid

Wallet:
+€50 exactly once
```

Verify:

* correct client
* correct tenant
* correct amount
* correct currency
* payment/provider reference stored
* wallet activity created
* no session revenue generated

---

# 2. Duplicate Success Event

Replay the same successful Stripe event.

Expected:

```text
Wallet before replay: +€50
Wallet after replay:  +€50
```

Not:

```text
+€100
```

There must be no duplicate ledger movement.

---

# 3. Failed Payment

Process a failed payment event.

Expected:

```text
wallet credit = €0
```

Top-up becomes the appropriate terminal failure state.

---

# 4. Expired Checkout

Process an expired Checkout/session event.

Expected:

```text
wallet credit = €0
```

The top-up must not remain eligible for later normal crediting.

---

# 5. Terminal → Late Success Protection

Explicitly verify the recently corrected scenario.

Example:

```text
pending
→ failed / cancelled / expired
→ later Stripe paid event arrives
```

Expected:

```text
top-up remains terminal
wallet credit = €0
```

Only:

```text
pending → paid
```

may create wallet value.

---

# 6. Tenant / Client Isolation

Create at least two clients.

A Stripe top-up created for Client A must:

* credit Client A only
* not affect Client B
* remain tenant-scoped
* not be transferable by modifying client-facing request data

Provider/payment metadata must resolve to the server-authoritative top-up record.

---

# 7. Revenue Separation

Verify explicitly:

```text
€50 Stripe wallet top-up
```

changes:

```text
wallet purchased value: +€50
```

but does **not** change:

```text
Marcus settled session revenue
```

A wallet purchase is not training revenue under the current reporting model.

---

# 8. Wallet Activity

After successful payment, verify the client sees an activity record equivalent to:

```text
Training value added
+€50
```

Use existing product terminology.

Do not expose unnecessary Stripe internals.

---

# 9. Investigate Existing 500 Fixture Failures

The full integration suite currently reports three fixture/setup failures involving:

* commercial
* notifications
* training bookings

where manual-value setup requests return `500`.

Do not assume these are unrelated.

For each failure:

1. Reproduce it independently.
2. Capture exact endpoint/request.
3. Inspect server error/log.
4. Establish root cause.
5. Determine whether it was introduced by:

   * wallet schema changes
   * migration state
   * fixture assumptions
   * new commercial constraints
   * unrelated pre-existing test setup

Fix the smallest proven cause.

Do not weaken commercial validation to make tests pass.
